# PF-08B0 — Idempotency infrastructure design

## Decision

PF-08B0 introduces one additive table, `public.business_operation_idempotency`, shared by future Store checkout and MoviBack redemption transactions. It creates no checkout/redemption RPC and changes no route or business mutation.

The model is intentionally small:

| Column | Type | Purpose |
|---|---|---|
| `id` | UUID | Stable internal row identity; generated by PostgreSQL |
| `operation` | text | Constrained to `store_checkout` or `moviback_redemption` |
| `user_id` | UUID | Server-authenticated MOVIPadel user; FK to `public.users` |
| `idempotency_key` | UUID | Client-generated key retained across retries |
| `request_hash` | text | Lowercase 64-character SHA-256 digest of canonical request intent |
| `status` | text | `processing` while the owning transaction runs; `committed` at successful completion |
| `result` | JSONB | Minimal stable successful result needed for replay |
| `created_at` | timestamptz | Claim creation time |
| `completed_at` | timestamptz | Successful completion time |

There is no `failed` state. A failed future business transaction must raise/roll back, removing its uncommitted claim with all business writes.

## Scoped uniqueness

The exact uniqueness boundary is:

```text
UNIQUE (operation, user_id, idempotency_key)
```

Therefore:

- the same operation/user/key can own only one durable result;
- the same UUID key used by another user is independent;
- the same UUID key used for the other operation is independent;
- a new key remains a new business request even when its payload is identical.

The unique index backing this constraint is also the concurrency primitive. Concurrent inserts for the same scope serialize on PostgreSQL's unique-index conflict handling; no advisory lock is required.

## Claim, replay, and conflict protocol

Future checkout/redemption RPCs must perform this protocol inside the same database transaction as all business mutations:

1. Attempt an insert with `status='processing'` using `INSERT ... ON CONFLICT (operation,user_id,idempotency_key) DO NOTHING RETURNING ...`.
2. If inserted, this is a **NEW REQUEST**. Continue the transaction.
3. If not inserted, select the existing scoped row.
4. If its `request_hash` differs, return/raise a stable idempotency conflict that the route maps to HTTP 409. Perform no business writes.
5. If its hash matches and status is `committed`, return the stored result as an **IDENTICAL REPLAY**. Perform no business writes.
6. If it was the new claim, execute all validated business writes, then set `status='committed'`, store the minimal result object, and set `completed_at` before returning.

When a concurrent transaction owns the same uncommitted unique key, step 1 waits. If the owner commits, the waiter inserts zero rows and reads the committed result. If the owner rolls back, the waiter may acquire the new claim and process the request.

## Status and rollback semantics

`processing` and `committed` are the only states. A CHECK constraint enforces:

- `processing` → `result IS NULL` and `completed_at IS NULL`;
- `committed` → result is a JSON object and `completed_at >= created_at`.

The claim, business mutation, and final result must never be split across transactions. A disconnected/aborted transaction is rolled back by PostgreSQL, so it leaves no misleading claim. A durably visible `processing` row would mean a caller violated the protocol by committing early; future RPC code must treat that as an internal invariant failure, not as replay or conflict.

## Canonical request hash

The application/server integration added later must produce a versioned canonical request representation, encode it as UTF-8, calculate SHA-256, and pass the lowercase 64-character hexadecimal digest. The database validates the digest format and compares the stored value; it does not trust arbitrary JSON key iteration order.

Recommended canonicalization rules:

- use an explicit schema version such as `v: 1`;
- use fixed field names and types;
- normalize enums to their accepted database values;
- represent absent nullable IDs explicitly as JSON `null`;
- normalize optional text consistently, including the chosen empty-string/null policy;
- reject duplicate cart identities or aggregate their quantities;
- sort aggregated cart lines by product ID, color ID, nullable size ID, then quantity;
- serialize with a deterministic canonical JSON algorithm or an explicitly ordered byte format;
- include only client request intent validated by the server.

Checkout intent should include normalized pickup club, payment mode, requested point usage, notes policy, and sorted product/color/nullable-size/quantity lines. Redemption intent should include reward ID, color ID, and nullable size ID.

Do not include the authenticated user ID, operation, or idempotency key in the digest because they are already part of the scoped lookup; including operation as part of the versioned envelope is harmless defense-in-depth. Do not include mutable server-authoritative prices, stock, current status, generated QR values, result IDs, headers, cookies, tokens, or provider data. Excluding mutable catalog state ensures a retry after commit replays the original outcome instead of conflicting because data later changed.

## Stored result

`result` is JSONB so each future operation can store the smallest stable success contract required to reproduce its response:

- checkout: order ID and authoritative committed totals/response fields;
- redemption: redemption ID, QR token, optional fulfillment order ID, and authoritative response fields.

The route derives `created` versus `replayed` from claim outcome; it need not be frozen into the result. Notification delivery state is not stored. Notifications remain post-commit and should normally be scheduled only for a newly created result.

## Security

- Owner: `postgres`.
- RLS: enabled.
- Policies: none; there is no browser-direct row path.
- `PUBLIC`, `anon`, and `authenticated`: all table privileges explicitly revoked.
- `service_role`: only SELECT, INSERT, UPDATE, and DELETE.
- `service_role`: no TRUNCATE, REFERENCES, or TRIGGER privilege.
- The migration creates no function and grants no RPC execution.

Supabase defaults initially gave `service_role` broader table privileges. Local validation caught this, and the migration now explicitly revokes all service-role privileges before granting only CRUD.

The future server route must continue validating the signed cookie and pass its derived user ID. Browser input must never choose a different user identity, and the service-role credential must remain server-only.

## Future integration boundaries

PF-08B1 checkout integration must claim operation `store_checkout`, complete the claim in the same transaction as order/items/debit/stock, and replay only the stored checkout result.

Future redemption integration must claim operation `moviback_redemption`, complete the claim in the same transaction as redemption/debit/inventory/fulfillment, and replay only the stored redemption result.

Neither integration is implemented by PF-08B0.
